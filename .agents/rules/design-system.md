# Connectdesk Design System Rules

---

# Purpose

These rules define the design system for Connectdesk.

Every UI generated by the AI must follow these rules. All visual values come from `tokens/variables.css` — never hardcode colors, typography, radii, shadows, elevation, or spacing.

The design system prioritizes usability for customer support specialists who spend long hours using the application.

---

# Design Philosophy

The UI should be clean, modern, professional, fast, consistent, accessible, and data-focused. Every screen should help users complete tasks quickly with minimal cognitive load.

Avoid unnecessary decoration. The interface should feel calm and productivity-focused.

---

# Token Reference

All visual design values are defined as CSS custom properties in `tokens/variables.css`. Import this file at the application root and reference these variables everywhere.

## Colors

Colors use Material Design 3 semantic token naming. Light and dark themes are handled via `[data-theme="dark"]`.

## Typography

Font family: **Poppins**, fallback `sans-serif`.

| Token                          | Size   | Weight | Use                              |
|--------------------------------|--------|--------|----------------------------------|
| `--font-display-large`         | 64px   | 400    | Landing/hero, large dashboards   |
| `--font-display-medium`        | 54px   | 400    | Major section headers            |
| `--font-display-small`         | 44px   | 400    | Page-level headers               |
| `--font-headline-large`        | 40px   | 400    | Page titles                      |
| `--font-headline-medium`       | 36px   | 400    | Section titles                   |
| `--font-headline-small`        | 32px   | 400    | Card titles, dialog headers      |
| `--font-title-large`           | 14px   | 400    | List item headings               |
| `--font-title-medium`          | 12px   | 400    | Sub-headings, labels             |
| `--font-title-small`           | 11px   | 400    | Captions, overlines              |
| `--font-body-large`            | 16px   | 400    | Body text, descriptions          |
| `--font-body-medium`           | 14px   | 400    | Default body, table cells        |
| `--font-body-small`            | 12px   | 400    | Helper text, secondary info      |

Prefer `--font-body-medium` (14px) for most content. Use `--font-headline-small` (32px) for page titles, `--font-body-large` (16px) for lead paragraphs.

All font weight tokens default to 400. For headings and emphasis (page titles, section headers, card titles), apply `font-weight: 600` to maintain clear visual hierarchy while the token system provides the sizing.

## Spacing

Use an 8-point system via `--spacing-*` tokens from `tokens/variables.css`. Consistent spacing is visual — apply uniform padding and margin.

| Token         | Value  | Use                                      |
|---------------|--------|------------------------------------------|
| `--spacing-1` | 4px    | Icon gaps, tight inline spacing          |
| `--spacing-2` | 8px    | Inner gaps within compact components     |
| `--spacing-3` | 12px   | Small component padding                  |
| `--spacing-4` | 16px   | Default component padding, card padding  |
| `--spacing-5` | 20px   | Medium gaps between related elements     |
| `--spacing-6` | 24px   | Section gaps                             |
| `--spacing-8` | 32px   | Between major sections                   |
| `--spacing-10`| 40px   | Page-level section breaks                |
| `--spacing-12`| 48px   | Large section separators                 |
| `--spacing-16`| 64px   | Page-level spacing, hero sections        |

# Breakpoints

| Name          | Min width |
|---------------|-----------|
| Mobile        | 0px       |
| Tablet        | 640px     |
| Desktop       | 1024px    |
| Large Desktop | 1440px    |

Design mobile-first. All screens must work on tablet and desktop. Tables should adapt gracefully on smaller screens. Prioritize touch-friendly targets (minimum 44px).

---

# Dark Mode

Dark mode uses the `[data-theme="dark"]` attribute on the root element. All color tokens switch automatically.

Components must not use hardcoded colors. Always reference CSS custom properties so they adapt to theme changes.

```css
/* Correct */
.card { background: var(--color-surface-color); color: var(--color-on-surface-color); }

/* Wrong */
.card { background: #ffffff; color: #1a1a1a; }
```

Test every component in both light and dark themes before considering it complete.

---

# Icons

Use **Lucide React** icons. Icons should include accessible labels, support recognition, and remain visually consistent. Avoid decorative icons — every icon should convey meaning.

---

# Component Patterns

## Buttons

Use `--color-primary-color` background for primary actions. Use `--color-error-color` for destructive actions.

Button hierarchy: **Primary** (main action) → **Secondary** (alternative) → **Outline** (less prominent) → **Ghost** (low emphasis).

Destructive buttons use `--color-error-color` for delete, remove, and archive actions.

Loading buttons must show a loading indicator. Disabled buttons should indicate why they are unavailable when appropriate.

## Forms

Every form includes: labels, placeholder text where helpful, helper text when necessary, validation messages, required field indicators, disabled states, loading states, and success states.

Never rely on placeholders as labels. Group related fields together.

Use `--color-error-color` for validation error text and borders. Use `--color-outline-color` for input borders.

## Input Components

Supported input types: Text Input, Textarea, Password, Search, Number, Email, Phone, Select, Multi Select, Date Picker, Checkbox, Radio, Toggle, File Upload.

All inputs must support validation states.

## Tables

Tables support: pagination, sorting, filtering, search, empty states, loading states, row actions, and bulk actions where applicable.

Use sticky headers for long tables. Row hover states use `--color-surface-variant-color`.

## Cards

Cards contain: title, optional description, content, and actions. Do not overload a single card with excessive information.

Card background: `--color-surface-color`. Card border: `--color-outline-variant-color`.

## Status Badges

Use consistent status indicators. Combine color with text.

**Ticket statuses:** Open, In Progress, Waiting, Escalated, Resolved, Closed
**Agent statuses:** Available, Busy, Away, Break, Offline
**QA statuses:** Pending Review, Passed, Flagged, Escalated

Map ticket "Open" to `--color-primary-container-color`, "Resolved" to `--color-tertiary-container-color`, "Escalated" to `--color-error-container-color`, etc.

---

# Data Visualization

Used SPARINGLY — only when charts improve understanding.

Supported chart types: Line, Bar, Area, Donut, Progress Indicators. Avoid pie charts in most cases.

Every chart includes: title, labels, legends where necessary, empty state, and loading state.

Chart colors should use the primary and secondary color tokens. For multi-series charts, derive additional colors from the palette rather than introducing new hardcoded values.

# Notifications

| Priority | Token                           | Examples                                    |
|----------|---------------------------------|---------------------------------------------|
| Critical | `--color-error-color`           | System failures, security alerts, SLA breaches |
| High     | `--color-primary-color`         | Escalations, approval requests              |
| Medium   | `--color-secondary-color`       | Ticket assignments, QA feedback             |
| Low      | `--color-on-surface-variant-color` | Knowledge base updates, informational messages |

Notifications should be concise and actionable.

---

# States

## Empty States

Every page that can be empty must include a meaningful empty state with a friendly message, brief explanation, and primary action if applicable. Never show a blank screen.

## Loading States

Every async operation must provide loading feedback: skeleton loaders for content areas, progress indicators for page loads, and loading spinners for buttons. Avoid layout shifts during loading.

## Error States

Error messages should explain the issue clearly, suggest the next step, and avoid technical jargon. Provide retry actions where appropriate. Use `--color-error-color` for error messaging.

# Reusable Components

The following domain-specific components should be built once and reused throughout the application:

- Ticket Card, Customer Card, Agent Card, Company Card
- Conversation Panel, Customer Timeline
- Call Controls, Chat Window
- QA Scorecard, QA Rubric
- KPI Card, SLA Indicator, Activity Timeline
- Integration Status Card
- Notification Center
- Knowledge Base Article Card

Before building any new component, check if one already exists in the codebase or in the design system.

---

# Navigation

Primary navigation should remain consistent. Support sidebar navigation, top navigation, and breadcrumbs. Highlight the active page. Collapse navigation on smaller screens.

---

# Dashboard Design

Dashboards should surface the most important information first, in this order:

1. KPIs
2. Alerts
3. Tasks
4. Charts
5. Tables
6. Recent Activity

Avoid overwhelming users with unnecessary metrics.

---

# Accessibility

Every interface must support keyboard navigation, include visible focus states, use semantic HTML, include ARIA attributes where needed, and meet WCAG AA contrast standards. Accessibility is mandatory, not optional.

Focus states: use a visible outline or glow. Default focus indicator uses `--color-primary-color` with `--shadow-glow-primary`. Never remove focus outlines without providing an equally visible alternative.

```css
*:focus-visible {
  outline: 2px solid var(--color-primary-color);
  outline-offset: 2px;
}
```

---

# Final Rule

Every generated UI must be consistent, accessible, responsive, reusable, easy to understand, and production-ready. All visual values must reference tokens from `tokens/variables.css`.

If a design decision conflicts with the PRD or AGENTS.md, follow the PRD first, then AGENTS.md, and finally these design system rules.
